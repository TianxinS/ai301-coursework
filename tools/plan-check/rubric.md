# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-matches-repro | The plan's stated cause, read against what the repro evidence shows (its observed output: error, value, and location) | The stated cause explains the failure the repro evidence actually shows (same error or wrong value, in the same place), and nothing in the repro evidence contradicts it. A cause the repro evidence does not support fails, however plausible it sounds. If the plan states its cause as one possibility among others, judge whether the repro evidence supports the one the approach acts on. | required |
| scope-bounded | The plan's scope statement and its list of files to touch, read against the plan's stated cause and the issue | The plan says where it will change code (files, or where the exact file is not yet pinned, the component plus how it will be pinned), says what it will not change, and every change it commits to is part of fixing the stated cause. A change at another site of the same defect, named by the issue or by the plan with its location, is part of the fix. Reading or auditing code and reporting findings without changing them is not a change. Fail if the plan commits to changes the cause does not require (refactors, cleanups, redesigns, extra features) or leaves open what else might change ("and any related code"). | required |
| approach-fixes-cause | The plan's approach, read against its stated cause and the repro evidence | The described change removes the cause the diagnosis names. Fail if it only hides the symptom the repro shows: loosening or deleting an assertion, skipping or xfailing a test, catching and silencing the error, or special-casing the repro's exact input. | required |
| plan-executable | The plan's approach and list of files to touch | A stranger could start the change from the plan alone: the edit itself is decided (what will be added, changed, or removed) and its location is named, either as a file and function, test, or fixture, or, when the exact function can only be found by tracing, as a named component plus the concrete method the plan will use to pin it. Fail if the edit itself is left undecided ("fix the logic in the scorer", "update the tests as needed") or the location is open-ended with no way to find it. | required |
| test-plan-observable | The plan's test plan, read against the repro evidence's steps and observed output | The test plan re-runs the repro steps (or a check that runs the real code with the repro's inputs) and states the specific output expected after the fix, which differs observably from the repro's observed failure. It does not need to add a new automated test. Fail if it only says "run the tests" or "confirm it works", or names no expected output. | required |
| unknowns-honest | Every claim the plan states as fact (in its cause, change, test, and any risks or unknowns it lists), read against the repro evidence | Nothing the plan states as certain is contradicted by the repro evidence, and the plan does not guarantee an outcome it has no way to know yet (e.g. "this cannot affect anything else", "this is the only place the bug occurs"). A plan does not need a risks section to pass; an inference that follows from the repro evidence, or a side effect the test plan says it will check, is not false confidence. | required |
| comment-fits-thread | The plan comment, read against the thread highlights, the plan itself, and the repo-facts block (contribution policy, AI-use policy, stated conventions) | The comment describes the same plan as the plan file; is in the author's own words (not "same approach as above" or a restatement of another commenter's plan); does not ignore or contradict a direction a maintainer gave in the thread; and follows the conventions the repo-facts block states. If the stated policy requires disclosure of any AI usage, the comment must contain a disclosure statement (the tool and extent of assistance, or a statement that none was used); a comment with no disclosure fails, because the grader cannot know AI was not used. If the repo facts state a gate on the next step the comment announces (e.g. a vouch or approval flow before PRs are accepted, an issue-first rule), the comment must acknowledge it rather than announce the PR as if the gate did not exist. A convention that is only linked and whose text is not shown is not held against the comment. | required |

## Verdict rule

Accept (ready) if every required check passes. There are no preferred checks.

Reject (hold) if any required check fails or is unclear. Grade a check unclear only when the evidence it needs is missing or cut off in the package, such as a plan with no test plan section or a truncated repro output. When the evidence is present and the call is just hard, grade pass or fail and give the reason; do not use unclear to avoid a judgment.
